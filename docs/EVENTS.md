# Domain events

Catalog of domain events the platform will raise. Storage: the `events`
outbox table (platform migration `0004_events.sql`), written in the same
transaction as the aggregate change. Go side: `internal/sharedkernel`
(`DomainEvent`, `AggregateRoot.Raise`). Most are still aspirational — the
contract to implement against — except **`TicketClosed`** and the
inventory→ledger GL posting events (see "Live events" below), wired as
part of `openspec/changes/split-inventory-microservice`: pos and platform
share one Postgres database/schema in this increment, so pos's outbox
rows land in the same `events` table platform's migration created; a
`pkg/outbox.Poller` in `cmd/aivo-server` delivers them over gRPC.

ERD: interactive [docs/erd.html](./erd.html) · static [docs/db/schema.svg](./db/schema.svg) (generated by tbls, see `.tbls.yml`).

## Live events

### `TicketClosed` (pos → inventory)

Published by `internal/pos/app.App.CloseTicket` in the same transaction
as the ticket close (`internal/pos/events.TicketClosedPayload`); consumed
by `cmd/aivo-inventory`'s `InventoryService.HandleTicketClosed` gRPC RPC
(`backend/proto/inventory/v1/inventory.proto`), delivered by a
`pkg/outbox.Poller` running in `cmd/aivo-server`
(`internal/pos/adapters/inventorygrpc.Deliverer`). Idempotency key:
`ticket_id`.

```json
{
  "restaurant_id": "uuid",
  "ticket_id": "uuid",
  "closed_by": "uuid",
  "business_date": "YYYY-MM-DD",
  "lines": [{"menu_item_id": "uuid", "qty": 2, "ticket_line_id": "uuid"}]
}
```

Ticket close commits and returns success even if `cmd/aivo-inventory` is
unreachable; the event stays pending in the `events` table and is
delivered once inventory becomes reachable (service-events spec).

### Inventory→ledger GL postings (inventory → aivo-server)

Every inventory action that results in a GL entry — sale COGS, receipt,
write-off, stocktake adjustment, and reversal of any of those — is
published from inventory's own outbox (its own `inventory` schema, once
`cmd/aivo-inventory` exists) and delivered to `cmd/aivo-server`'s
`:9080` gRPC listener, `LedgerService`
(`backend/proto/ledger/v1/ledger.proto`,
`internal/ledger/adapters/grpcserver.Server`):

| RPC | Idempotency key | Ledger source kind |
|---|---|---|
| `PostCOGSJournal` / `ReverseCOGSJournal` | ticket_id | `cogs` |
| `PostReceiptJournal` / `ReverseReceiptJournal` | receipt_id | `inventory_receipt` |
| `PostWriteOffJournal` / `ReverseWriteOffJournal` | write_off_id | `inventory_writeoff` |
| `PostStocktakeJournal` / `ReverseStocktakeJournal` | stocktake_id | `inventory_stocktake` |

Every RPC is idempotent on its request's source id: a redelivery finds
the already-live document for that source and returns its id without
posting/reversing again (`ledger.LiveDocumentBySource`, backed by a
`journal_documents (source_kind, source_id) WHERE state <> 'cancelled'`
unique index covering every source kind, not just shift acceptance).

## Conventions

- Names: past tense, `PascalCase`, stable once published (consumers depend on them).
- `payload` is flat JSON, IDs as strings; no nested aggregates — consumers re-read state they need.
- `restaurant_id` column set for tenant-scoped events; NULL only for org-level (`OrganizationRegistered`, `SubscriptionChanged`).
- Publisher (когда появится): poll `events_pending`, deliver, set `published_at`; at-least-once, consumers idempotent by `id`.
