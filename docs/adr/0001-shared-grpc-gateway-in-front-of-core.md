# Satellite frontends have no backend of their own; a shared grpc-gateway sits in front of the Go core

Every satellite frontend (web-menu now; backoffice, POS, waiter app later) talks to the Go backend core over gRPC internally, but public browser traffic is REST/JSON — not gRPC-Web. Rather than each satellite service growing its own backend/BFF to bridge that gap, a single shared layer generated by [grpc-gateway](https://github.com/grpc-ecosystem/grpc-gateway) sits in front of the core: the `.proto` files are the one source of truth, and grpc-gateway generates the REST/JSON reverse-proxy from them alongside the gRPC server itself — no hand-maintained REST↔gRPC mapping, no separate Envoy/API-gateway deployment.

This was surprising enough, and hard enough to reverse once satellite services start depending on it, to warrant recording. Alternatives considered: Envoy + gRPC-Web (rejected — makes the browser gRPC-Web-native instead of plain REST/JSON, and adds a full Envoy deployment); a hand-rolled gateway service (rejected for now — cheapest to start, but nothing keeps its REST↔gRPC mapping in sync with the proto as endpoints grow); a full API gateway product like Kong/Traefik (rejected for now as disproportionate infra for the current scale — revisit once cross-service routing/auth/rate-limit policy complexity justifies it).

Public (diner, anonymous, high-volume) and staff (authenticated, low-volume) traffic share this same gateway stack, but their auth/rate-limit *policy* is kept separate from day one even though the tech is shared — retrofitting that separation later is the expensive path. Diner-side auth (an anonymous, table-scoped session token) is detailed in the Menu map's "Diner session & rate-limiting design" ticket; staff-side auth is deferred to the future Backoffice map.
