# AIVO RMS: сводная архитектура (интеграция domain / events / edge)

Интеграционный документ поверх трёх проектных отчётов:
[domain.md](./domain.md) (новые домены), [events.md](./events.md)
(outbox → Kafka), [edge.md](./edge.md) (локальный узел ресторана), с учётом
[ddd-architecture.md](../ddd-architecture.md) (текущий синтез + топ-10 долгов).
Код не меняется; это план.

## 1. Целевая картина одним экраном

```
            ГОСТЬ (свой телефон, LTE) ──► всегда в ОБЛАКО: /{slug}/menu, заказы, handoff
┌─ ОБЛАКО ── один Go-бинарь MODE=cloud + Postgres ─────────────────────────────────────┐
│                                                                                      │
│  Platform (тенанты, auth, РОЛИ×6, биллинг, темы, customers, AI-ассистент)            │
│    │ upstream                                                                        │
│  ┌─▼────┐  conformist/menubridge  ┌─────────────────────────────┐                    │
│  │ Menu │◄────────────────────────│ POS  (+Kitchen/KDS,          │                    │
│  └──────┘                         │  +payments/касса/Z-отчёт)    │                    │
│                                   └──────────────┬──────────────┘                    │
│          все контексты пишут события ─────────────▼                                  │
│  ┌──────────────────────────────────────────────────────────────────────┐            │
│  │  OUTBOX `events` (Postgres, +seq) — ИСТОЧНИК ИСТИНЫ СОБЫТИЙ          │            │
│  └───────┬──────────────────────────────────────────────┬───────────────┘            │
│   этап 0: in-process диспетчер              этап 1+: relay-поллер ─► KAFKA           │
│   (Go-хендлеры в том же процессе)           aivo.{ctx}.events, key=restaurant_id,    │
│          │                                  12 партиций, retention 30д               │
│  ┌───────▼──────────┐ ┌───────────────┐ ┌──────────────────┐                         │
│  │ Inventory (склад, │ │ Workforce     │ │ Loyalty (org-     │◄─ синхр. порт из POS  │
│  │ тех-карты,закупки)│ │ (график,      │ │ scoped баллы,     │   (промо/списание)    │
│  │ ← TicketClosed    │ │  табель)      │ │ промо)            │                        │
│  └──────────────────┘ └───────────────┘ └──────────────────┘                         │
│  Finance (P&L) — отчётный контекст поверх pos/inventory/workforce (порты-читалки)    │
│                                                                                      │
│  POST /sync/events (идемпотентно, дедуп по event UUID) ─► проекции + тот же outbox   │
└─────────▲──────────────────────────────────────────────┬─────────────────────────────┘
          │ факты: append-only события                    │ состояние: версионированные
          │ (sync_outbox → HTTP push, ретраи)             ▼ снапшоты (каталог, цены,
┌─ EDGE ── ресторан, mini-PC ────────────────────────────── сотрудники, промо; rev+swap)┐
│  тот же aivo-server, MODE=edge + локальный Postgres (те же миграции/sqlc)            │
│  поднимает ТОЛЬКО: pos (смены, тикеты, оплаты, KDS, печать) + read-only проекции     │
│  каталог правится только в облаке; stop-list — локальный оверлей                     │
│  офлайн недоступно (честная ошибка): handoff, сервис-запросы, списание баллов        │
│  Kafka/NATS на edge — НЕТ. Терминалы = тонкие клиенты по локальному Wi-Fi            │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

Ключевые инварианты картины:

- **Истина событий — Postgres outbox** (events.md, главный принцип); Kafka —
  заменяемый транспорт, появляется только с первым консьюмером вне процесса.
- **Облачный вызов на кассовом пути запрещён** (edge.md §2) — архитектурный
  инвариант, а не настройка.
- **Single writer на каждый класс данных** (edge.md §4): pos-сущности
  ресторана пишет его edge, каталог/справочники — облако, пересечений нет.
- Новые контексты (inventory, workforce, finance, loyalty) — **только облако**;
  на edge живёт исключительно кассовый путь (pos + KDS как его подпакет).

## 2. Противоречия между отчётами и вердикты

### К1. Транспорт edge-синка vs Kafka-топология: две шины?

- **events.md**: единственный тракт — outbox `events` → relay → Kafka
  (§0–§2), «истина в Postgres».
- **edge.md §3.3**: edge шлёт события по HTTP в `POST /sync/events`, Kafka/NATS
  на edge отвергнуты; «где потребуется веер в облаке — sync-endpoint публикует
  принятые события в облачную шину».

**Вердикт: это не два конкурирующих транспорта, а два плеча одного тракта, но
их надо явно склеить: sync-endpoint облака применяет события edge к проекциям
и в той же транзакции вставляет их в облачный outbox `events`** (сохраняя
edge-сгенерированный event UUID — он же ключ дедупликации `ON CONFLICT DO
NOTHING`). Дальше события едут стандартным путём events.md (диспетчер/relay),
и ни один облачный консьюмер (inventory, CRM, аналитика) не знает, родилось
событие в облаке или на edge.

Почему так: (а) сохраняется единственный источник истины — облачный outbox
полон для любого консьюмера; (б) HTTP-плечо edge→cloud обосновано в edge.md
§3.3 (durable-запись обязана быть в одной транзакции с продажей — брокер это
не даёт, outbox нужен всё равно); (в) требование: **конверт события в
`sync_outbox` edge = конверт outbox облака** (events.md §3 — id, name,
version, aggregate, restaurant_id, occurred_at, payload), чтобы вставка была
тривиальной. Это уточнение к схеме `sync_outbox` из edge.md §3.1, где
перечислены только `(id, seq, type, payload, occurred_at)`.

### К2. KDS: экран pos или внешний Kafka-консьюмер?

- **domain.md §6**: KDS — расширение pos (те же ticket_lines, «двух правд о
  статусе строки не заводим»), экран `/kds`, поллинг.
- **events.md §5**: KDS — будущий консьюмер-группа `kds` на топиках Kafka, и
  в §0 «KDS» назван возможным триггером этапа 1.

**Вердикт: побеждает domain.md — KDS в MVP это экран pos-контекста, без Kafka
и без консьюмер-группы.** Строка из таблицы консьюмеров events.md §5
остаётся «спящей» и не является триггером этапа 1. Почему: (а) у KDS нет ни
одной собственной сущности — Kafka-проекция означала бы вторую правду о
статусе строки, ровно то, чего domain.md избегает; (б) решающий аргумент —
edge: KDS обязан работать в офлайне (повар готовит, когда интернета нет), а
Kafka-консьюмер на edge невозможен по вердикту edge.md §3.3. KDS внутри pos
автоматически едет на edge бесплатно. Kafka-KDS вернётся в повестку, только
если KDS станет отдельным устройством со своим процессом — тогда это и есть
честный триггер этапа 1 по events.md.

### К3. Обогащённый `TicketClosed` vs конвенция «payload плоский, консьюмеры перечитывают состояние»

- **EVENTS.md / events.md §3**: payload плоский, без вложенных агрегатов,
  консьюмер дочитывает состояние из БД/API.
- **domain.md** (§1, §4a, §7): `TicketClosed` надо обогатить строками
  `[{menu_item_id, qty}]`, payments `[{method, amount, tip}]` и discounts —
  этого ждут inventory (FIFO-списание), finance и loyalty.

**Вердикт: обогащаем `TicketClosed` — фиксируем это как задокументированное
исключение из конвенции, а не её отмену.** Почему: у события три консьюмера в
трёх контекстах, и «перечитай ticket_lines» создаёт скрытую зависимость от
порядка применения проекций (особенно для событий, приехавших с edge: консьюмер
в облаке перечитывает не оригинал, а sync-проекцию — она обязана быть уже
применена). Снапшот в payload делает событие самодостаточным фактом — та же
логика, по которой ticket_lines уже снапшоты (edge.md §0). Правило дальше:
плоский payload по умолчанию; вложенные строки — только когда событие потребляют
≥2 контекста или офлайн-тракт, с фиксацией в EVENTS.md.

### К4. Loyalty: «синхронный порт pos→loyalty в транзакции закрытия» vs «облачный вызов на кассовом пути запрещён»

- **domain.md §5**: списание баллов — синхронный вызов `pos → ports.Loyalty`
  внутри транзакции закрытия тикета; баланс org-scoped (живёт в облаке).
- **edge.md §2**: любой синхронный облачный вызов на кассовом пути запрещён.

Это прямой конфликт для ресторана на edge: закрыть тикет со списанием баллов
без связи нельзя. **Вердикт: разводим по типам скидок.**

1. **Промо-правила** (percent_off_ticket, happy hours) — реплицируются на edge
   потоком cloud→edge как ещё один версионированный снапшот (edge.md §3.2);
   pos и так считает скидку «на своей стороне, кладя снапшот в
   ticket_discounts» (domain.md §5) — работает офлайн без изменений.
2. **Списание баллов** — облачная операция того же класса, что handoff:
   синхронный вызов с таймаутом 3–5с, при офлайне — честная ошибка «баллы
   недоступны без связи», официант закрывает тикет без балльной скидки.
   Прецедент уже установлен edge.md §2 для handoff. Кэшировать баланс на edge
   нельзя: он org-scoped, писать его могут другие рестораны сети —
   это сломало бы single-writer-матрицу.
3. **Начисление** — событие `TicketClosed`, доедет с синком, идемпотентно;
   офлайн его не ломает.

В облачном режиме (пока edge нет) синхронный порт domain.md работает как
спроектирован — конфликт материализуется только на этапе edge, но контракт
(«redeem может вернуть недоступность») закладываем сразу, чтобы pos-код не
переписывать.

### К5. Очерёдность: три поэтапных плана друг другу не подчинены

- **domain.md §7**: волны 1–6, старт — оплаты (money path).
- **events.md §0**: этапы 0–2, старт — этап 0 «за несколько дней».
- **edge.md §7**: этапы 0–3, «этап 0 обязан случиться до любого другого».

Конфликтов три: (а) domain-волна 2 (inventory) требует доставленного
`TicketClosed` — то есть events-этап 0 должен пройти *до* неё, хотя ни один
план этого явно не требует; (б) edge-этап 2 наследует pos как money path —
делать его до payments (domain 4a) значит строить edge-кассу без денег и
переделывать; (в) events-этап 1 (Kafka) в events.md привязан к «первому
внешнему консьюмеру», которым там назван KDS — но по К2 KDS внешним не будет.

**Вердикт — единая последовательность (§3 ниже), с правилами:**
events-этап 0 и edge-этап 0 — немедленно, они дешёвые и разблокируют
остальное; payments + атомарный CloseShift — раньше edge-бинаря; Kafka
(events-этап 1) не привязана ни к какому релизу — её триггер теперь «первый
консьюмер, которому плохо в основном процессе» (реальные кандидаты: тяжёлая
аналитика или внешняя интеграция), и до этого момента вся система живёт на
этапе 0. Это допустимо потому, что контракт продюсеров/консьюмеров одинаков на
всех этапах (главное свойство events.md).

### К6. Новые события и топики: domain'у нужны, у events их нет

events.md §2 фиксирует три топика (`aivo.{platform,menu,pos}.events`) и
каталог EVENTS.md без единого события новых контекстов. domain.md §7 приносит
12 новых: обогащённый `TicketClosed`, `GoodsReceiptPosted`, `StockWrittenOff`,
`StocktakePosted`, `CashOperationRecorded`, `TimeEntryClosed`, `PointsAccrued`,
`PointsRedeemed`, `LineReady`, `LineServed`, `PurchaseOrderSent`,
`SupplierPriceIncreased`.

**Вердикт: противоречия нет — есть недописанный каталог; правила events.md
масштабируются механически.** Дополнения: топик на каждый новый контекст по
мере его появления (`aivo.inventory.events`, `aivo.workforce.events`,
`aivo.finance.events`, `aivo.loyalty.events`) — по правилу «топик = bounded
context» из events.md §2; ключ — `restaurant_id`, **кроме loyalty: там ключ
`org_id`** (баллы org-scoped, порядок транзакций счёта гостя важен в пределах
организации — тот же принцип, по которому org-события платформы едут с
`key=org_id`). `LineReady`/`LineServed` в outbox не пишем, пока их потребитель —
поллинг pos/state (domain.md §6 сам это допускает): событие без консьюмера —
ровно тот event bus поверх пустого outbox, который запрещает
ddd-architecture.md. EVENTS.md пополняется в том релизе, где событие впервые
проводится, не заранее.

## 3. Единый роадмап R1..R7

Обозначения долгов — номера топ-10 из ddd-architecture.md §6.
Правило слияния: сначала то, что (а) чинит текущие потери денег/данных,
(б) разблокирует максимум последующего.

### R0 — гигиена (дни; можно внутри R1, но ничего не релизится без неё)

- Убрать тихий мок-фолбэк в `frontend/pos/src/api.ts` → офлайн-баннер
  (edge-этап 0; прямо сейчас обрыв сети = молчаливая потеря продаж).
- Правки EVENTS.md: убрать `code` из `HandoffCreated`, добавить недостающие
  события (**долг 10, первая половина**).
- Долги **2** (дедуп сервис-запросов + развязка `pkg/session`),
  **4** (`ChangePlan` через `Transition`), **7** (судьба sqlc-генератов,
  удалить легаси menu/http). Долг 7 — не косметика: edge переиспользует
  `posdb`/миграции как есть (edge.md §1), двух слоёв стора быть не должно.

### R1 — «Деньги и живые события»

**Ценность ресторану: касса по-настоящему принимает оплаты — нал/карта, сдача,
чаевые, внесения/изъятия, честный Z-отчёт.**

- domain 4a: payments, ticket_discounts, cash_operations, новая формула
  `Shift.Close`; роли 3a (6 ролей, статическая матрица прав).
- **Долг 1** (атомарный CloseShift) — строго в этой же работе: формула
  expected расширяется, писать её дважды нельзя (domain.md §7); к тому же edge
  наследует CloseShift как источник истины Z-отчёта (edge.md §5).
- **Долг 3** (иммутабельность закрытого тикета) — payments требуют guard
  `status='open'` в любом случае.
- events-этап 0: колонка `seq`, in-process диспетчер, первые проводные
  консьюмеры — CRM-проекция (`OrderPlaced`/`TicketClosed`) и AI-аудит
  (**долг 10, вторая половина**). Kafka не поднимается.

Зависимости: только R0. Блокирует: почти всё дальнейшее.

### R2 — «Склад и food cost»

**Ценность: остатки, себестоимость FIFO, food cost — главный запрос «уровня
iiko» (domain.md §7).**

- Inventory MVP (domain §1) + поставщики без заявок (§2 MVP): номенклатура,
  тех-карты, накладные, списания, инвентаризация, книга движений.
- Консьюмер `TicketClosed` → FIFO-списание; обогащение payload (вердикт К3).
- Перед созданием первого нового контекста — **долг 8** (переезд доменов в
  `internal/<ctx>/domain`, CONTEXT-MAP.md): новые контексты рождаются сразу в
  целевой структуре, а не мигрируют потом. Заодно **долги 5, 9** (мелкие,
  app-слой).

Зависимости: R1 (доставка `TicketClosed` работает; выручка для food-cost-отчёта
берётся из payments). Блокирует: R6 (COGS для P&L).

### R3 — «Кухня (KDS)»

**Ценность: экран повара, статусы блюд, подсветка просрочки.**

- domain §6 MVP: одна станция, `fired → ready → served` на ticket_lines,
  экран `/kds` поверх существующего поллинга, `target_prep_minutes`.
- Без Kafka и без outbox-событий (вердикты К2, К6).
- **Долг 6** (handoff по местам: `AcceptHandoff` → `pos/app`, `CreateHandoff`
  → `menu/app`) — закрыть здесь, до edge: edge поднимает «только pos-контекст»
  (edge.md §1), и пока сага handoff лежит в HTTP-адаптере platform, граница
  pos для режимного запуска грязная.

Зависимости: R1 (роль `cook`). Мал и изолирован — при нехватке рук
переставим после R4 без последствий.

### R4 — «Офлайн-касса (edge)»

**Ценность: касса не падает из-за интернета — ключевое обещание надёжности.**

- edge-этап 1 (PWA-кэш + очередь IndexedDB) как быстрый мост, затем этап 2:
  `MODE=edge`, локальный Postgres, снапшоты каталога/сотрудников/промо,
  `sync_outbox` + `POST /sync/events` → **облачный outbox** (вердикт К1),
  business-date-отчётность, индикатор полноты, compose-профиль `edge` и
  демо-сценарий edge.md §6 как приёмочный тест.
- KDS и payments приезжают на edge автоматически (они внутри pos — итог R1/R3).

Зависимости: R1 (money path зафиксирован), долг 6 из R3, долг 7 из R0.
Kafka по-прежнему не нужна: sync-endpoint пишет в outbox, консьюмеры
in-process.

### R5 — «Персонал»

**Ценность: график смен, отметка прихода/ухода PIN-кодом, табель план/факт.**

- Workforce MVP (domain §3b): scheduled_shifts (EXCLUDE-constraint),
  time_entries, pos_pins. Роли уже есть с R1.
- Колонка `ticket_lines.added_by` — заложить здесь (единственное изменение pos
  ради будущей мотивации; сама мотивация — потом).
- Edge-оговорка: для ресторанов на edge clock-in должен работать офлайн ⇒
  time_entries edge-ресторана пишет edge (расширение single-writer-матрицы
  edge.md §4 одной строкой; факты едут тем же sync-трактом). Если R5 выйдет
  раньше массового edge — стартуем cloud-only и переносим при включении edge.

Зависимости: R1 (роли). Независим от R2–R4.

### R6 — «P&L»

**Ценность: владелец видит прибыль — выручка, food cost, списания, расходы.**

- Finance (domain §4b): expense_entries + PnL-отчёт через порты-читалки
  (`SalesReader`/`CogsReader`), labor — ручной строкой (автоматом из табеля —
  после появления ставок).
- Отчёты учитывают полноту edge-данных: «данные полны на момент X»
  (edge.md §5) — обязательная часть P&L, иначе владелец увидит «дыру» в
  выручке офлайн-дня.

Зависимости: R1 (payments) + R2 (COGS). R5 желателен, не обязателен.

### R7 — «Лояльность»

**Ценность: баллы за визиты, промо-скидки, баланс в ЛК гостя.**

- Loyalty MVP (domain §5): программа, счета, начисление по `TicketClosed`,
  списание при закрытии, percent_off_ticket.
- Контракт «redeem может быть недоступен» и репликация промо на edge —
  по вердикту К4. Топик/события loyalty — с ключом `org_id` (К6).

Зависимости: R1 (payments + ticket_discounts). Последний из MVP-контекстов —
монетизация лояльности слабее операционной боли склада и кассы.

## 4. Строим сразу vs сознательно откладываем

**При первой возможности** (дёшево и разблокирует): R0 целиком; колонка
`seq` в events; конверт события как стабильный контракт (общий для облака и
будущего edge — вердикт К1); guard'ы `status='open'`; `AUTO_CREATE_TOPICS=false`
и явное создание топиков — в тот день, когда Kafka вообще появится.

**Анти-скоуп** (сводно из трёх отчётов; у каждого пункта в отчёте назван
триггер пересмотра):

- *События (events.md §6):* event sourcing; exactly-once/Kafka-транзакции;
  Kafka Streams/Flink; Schema Registry; Debezium/CDC (до ~500 соб/с);
  compacted-справочники; кластер 3+ брокеров/multi-DC; авто re-drive DLQ,
  retry-топики, saga-оркестратор; LISTEN/NOTIFY для поллера.
- *Edge (edge.md):* CRDT; Kafka/NATS на edge; гостевое меню с edge (гость
  ходит в облако по LTE); handoff в офлайне; failover/вторая коробка edge;
  peer-to-peer синк терминалов — никогда; SQLite (только если железо заставит);
  toxiproxy (пока хватает `docker network disconnect`).
- *Домены (domain.md, по разделам):* план счетов и мульти-валюта; кастомные
  роли (конструктор прав); резервирование баллов; версии тех-карт;
  полуфабрикаты; мульти-склады; payroll/ставки; заявки поставщикам (Purchase
  Order) в MVP; EDI/email поставщику; сегменты гостей и рассылки; курсы/
  придержка на KDS; сверка эквайринга.
- *Из ddd-architecture.md:* Money-VO с валютами; generic-репозитории; полный
  ACL вместо menubridge; gRPC/микросервисы (ADR 0001 — пересмотр только для
  синхронных вызовов на events-этапе 2); физический перенос
  `CREATE TABLE restaurants`.

## 5. Риски топ-5

1. **Money path переделывается дважды.** Если payments (4a) и атомарный
   CloseShift (долг 1) делаются порознь, формула expected переписывается два
   раза, а между релизами живёт гонка потери денег
   (`pos/app/app.go:127-155`). *Митигейшн:* R1 объединяет их в один слайс;
   edge потом наследует готовый код без изменений.
2. **Продажи теряются прямо сейчас.** Мок-фолбэк POS (`api.ts:71-86`)
   молча уводит официанта в песочницу при обрыве сети — риск не будущий, а
   действующий. *Митигейшн:* R0, один день работы; до R4 честный баннер хуже
   офлайн-кассы, но лучше тихой потери.
3. **Расползание событийного контракта.** Три пишущих места (облачные
   контексты, edge sync_outbox, sync-endpoint) и растущий каталог — при
   рассинхроне конвертов edge-события перестанут вливаться в общий тракт.
   *Митигейшн:* единый конверт (К1) как стабильный контракт; Go-типы payload
   в одном репозитории (компилятор вместо Schema Registry, events.md §3);
   additive-only правила; EVENTS.md обновляется в релизе проводки события.
4. **Доверие к food cost.** Отрицательные остатки + `estimated`-списания
   (domain.md §1) при небрежном вводе накладных дают мусорный food cost — а
   это флагманская ценность R2. *Митигейшн:* доля estimated-движений прямо в
   отчёте; инвентаризация как регулярный ритуал (модель фиксирует
   expected на момент post); алерт на высокий процент estimated.
5. **Продуктовый: шесть контекстов до валидации спроса.** Роадмап на год+
   строится по референсу iiko, без подтверждения, что пилотам нужен именно
   этот порядок (склад раньше офлайна? лояльность вообще?). *Митигейшн:*
   каждый релиз R1–R7 — самостоятельная ценность и точка сверки с пилотным
   рестораном; порядок R2↔R4 и судьба R7 — явные вопросы владельцу (§6);
   ничего из анти-скоупа не строится «раз уж рядом».

## 6. Открытые вопросы владельцу продукта

Только меняющие архитектуру, не бэклог фич.

1. **Фискализация.** Нужна ли фискальная регистрация чеков (54-ФЗ/аналоги в
   целевых странах)? Ни один из трёх отчётов её не касается, а она меняет
   payments (R1: чек ≠ просто payment-строка) и edge (R4: ККТ — локальное
   устройство, офлайн-очередь фискальных документов). Ответ нужен до R1.
2. **Порядок боли: food cost или офлайн?** R2 и R4 независимы — что пилотным
   ресторанам нужнее раньше? От ответа зависит, тратим ли мы R3–R4-окно на
   edge или на углубление склада (алерты min_stock, заявки).
3. **Эквайринг.** «Карта» в payments — ручная отметка или интеграция с
   платёжным терминалом? Интеграция тянет локальный драйвер терминала на edge
   (ещё один компонент кассового пути) и сверку эквайринга в finance — сейчас
   обе в анти-скоупе.
4. **Централизованные закупки сети.** Появится ли у организаций с несколькими
   ресторанами один закупщик/центральный склад? Это переводит inventory из
   restaurant-scoped в org-scoped (domain.md §2 явно называет это условием
   выделения отдельного контекста) — дешевле знать до схемы R2, чем мигрировать
   после.
5. **Лояльность офлайн.** Приемлемо ли «баллы нельзя списать без интернета»
   (вердикт К4)? Если нет — нужен лимитированный офлайн-кредит баланса на
   edge, а это осознанный отказ от строгого `balance >= 0` и заметно другая
   модель loyalty. Ответ нужен до R7, влияет на контракт redeem уже в R1.
