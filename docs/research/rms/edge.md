# Edge-узел: отказоустойчивая работа POS без интернета

Проектный отчёт. Референс — iiko: в ресторане стоит локальный сервер, iikoFront
работает при полном отсутствии интернета и синхронизируется с облаком, когда
связь есть. Целевой инвариант AIVO тот же: **кассовая операция (тикет, смена,
печать) не имеет права падать из-за интернета.**

Каталог топиков и новые бизнес-домены здесь не проектируются — где нужен
топик/событие, ссылка абстрактная («outbox-событие POS»).

Опора на текущий код:

- POS-контекст (`backend/internal/pos/`): смены и тикеты — маленькое, замкнутое
  ядро. `Ticket`/`Shift` — 2 агрегата, ~10 команд, единственная зависимость
  наружу — порт `ports.Menu` (каталог, столы, сервис-запросы), read-only кроме
  ack/dismiss.
- Тикет-строки **уже снапшоты** (`TicketLine`: name, unit_price_cents, options —
  копируются в момент добавления, `domain/pos/domain.go:95`). Это главный
  подарок текущей модели: продажа не ссылается на «живой» каталог, а фиксирует
  факт.
- POS-фронт — поллинг `GET /pos/state` каждые 5с с ETag (`frontend/pos/src/api.ts`).
- ⚠️ Сейчас при обрыве сети `api.ts` **молча переключается на мок-фикстуры**
  (Proxy-фолбэк, `api.ts:71-86`): официант продолжает «работать» с фейковыми
  данными, которые никуда не сохраняются. Для демо это было ок, для продукта —
  тихая потеря продаж. Любой этап ниже начинается с удаления этого фолбэка и
  честного офлайн-баннера.

## 1. Топология: что стоит в ресторане, что живёт в облаке

### Edge-узел = тот же Go-бинарь в режиме `edge`

Не отдельный «минимальный pos-сервис». Причины:

- POS-контекст уже вырезан по границе портов: `ports.Store` (Postgres) +
  `ports.Menu` (бридж). Edge-режим — это тот же `cmd/aivo-server` с флагом
  `MODE=edge`, который поднимает **только** pos-контекст + read-only проекцию
  каталога + раздачу POS SPA. Один модуль, одна сборка, один Docker-образ,
  один цикл релизов. Отдельный сервис = второй репозиторий зависимостей,
  второй CI, дрейф типов — и всё это до первого пользователя.
- ADR 0001 («no gRPC until a second process needs it») это не нарушает:
  второй процесс появился, но говорит он с облаком по HTTP/JSON — тем же
  протоколом, что и SPA, новый RPC-стек не нужен.

Роутинг внутри бинаря по режиму:

| Режим | Поднимает | Не поднимает |
|---|---|---|
| `cloud` (по умолчанию, = сегодня) | всё | — |
| `edge` | pos app+HTTP, локальный Store, каталог-проекция, auth-кэш сотрудников, sync-агент, раздача `/pos` | platform (регистрация, биллинг, темы), menu-паблишинг, admin SPA, гостевое меню, AI-ассистент, CRM, customer accounts, handoff |

### Разделение ответственности

**Только облако** (не критично к секундной доступности, требует общего
состояния всех тенантов):

- Админка и весь platform-контекст: организации, подписки, биллинг, темы,
  провижининг, staff-CRUD.
- Меню-паблишинг: редактирование каталога — только в облаке. Edge получает
  каталог read-only (см. §3, cloud→edge). Это решение «single writer»
  устраняет целый класс конфликтов (§4).
- Гостевое меню и заказы гостей (`/{slug}/menu`, table token) — гость ходит со
  своего телефона по мобильной сети в облако; edge для него не существует.
- Handoff, CRM, customer accounts, AI — всё завязано на облачные данные.

**Edge** (кассовый путь):

- Смены: open/close, ordinal, expected/declared/variance.
- Тикеты: create, add lines, fire, note, close-по-смене.
- Печать (кухня/пречек) — принтеры в локальной сети, драйвер живёт на edge.
- Проекция каталога (позиции+опции+цены), столов, сотрудников (PIN/пароль-хэш
  для локального логина официанта).
- Инбокс сервис-запросов — деградирует: запросы рождаются в облаке (гость →
  облако), edge их видит только при связи. Это приемлемо: гость без связи
  ресторана всё равно позовёт официанта голосом.

### СУБД на edge: SQLite vs локальный Postgres

**Рекомендация: локальный Postgres** (тот же `postgres:16`-контейнер, что в
dev-compose).

| | SQLite | Локальный Postgres |
|---|---|---|
| Переиспользование кода | ❌ весь `posdb` (sqlc) и миграции написаны под Postgres: `uuid`, `jsonb` (options), partial unique index (`один open ticket на стол`), `FOR UPDATE` для атомарного CloseShift — всё пришлось бы переписывать и держать в двух диалектах | ✅ работает как есть: те же миграции `migrations/pos`, тот же sqlc-код |
| Ops в ресторане | ✅ нулевой | ⚠️ один контейнер в compose на той же коробке; для mini-PC (4ГБ RAM) — нормально, iiko локально держит MS SQL Server |
| Мульти-терминал (этап 3) | ⚠️ один writer-процесс — терпимо, пока все пишут через edge-бинарь | ✅ без оговорок |

Двойной SQL-слой — это постоянный налог на каждую будущую фичу POS; один
контейнер Postgres — разовая цена. Ленивое решение — не менять СУБД.
Пересмотреть в пользу SQLite стоит только если целевое железо окажется слабее
mini-PC (планшет как edge) — тогда это осознанный проект по портированию
запросов, не дефолт.

Деплой-юнит ресторана: docker compose из двух контейнеров (`aivo-server
MODE=edge` + `postgres`) на любой коробке (mini-PC/NUC). Терминалы (телефоны
официантов) ходят на edge по локальному Wi-Fi.

## 2. Режимы деградации

### Полный офлайн (ресторан без интернета)

Работает (всё локально):

- открыть/закрыть смену, Z-отчёт (expected/declared/variance считаются на edge);
- тикеты: создать, добавить позиции из кэшированного каталога, fire, печать;
- логин официанта — по кэшу сотрудников (хэш пароля/PIN реплицирован с
  облака; новый сотрудник, заведённый в облаке во время офлайна, не сможет
  войти до синка — приемлемо).

Не работает и честно показывается в UI («нет связи с облаком»):

- **handoff от гостя** — код рождается и хранится в облаке; edge офлайн → POS
  не может ни превью получить, ни consume сделать. Тянуть handoff-стор на edge
  нельзя дёшево (гость пишет в облако, значит нужна встречная репликация
  «облако→edge в реальном времени» — ровно то, чего нет при обрыве). Официант
  принимает заказ голосом — как до цифровизации;
- сервис-запросы гостей (та же причина: рождаются в облаке);
- CRM-линковка тикета, свежие правки каталога, админ-операции.

**Меню гостя — из облака, не с edge.** Гость на своём LTE, облако для него
доступно даже когда ресторанный канал лежит. Раздавать гостевое меню с edge по
локальному Wi-Fi (mDNS, самоподписанные сертификаты, captive portal) — большая
инженерия ради сценария «и у ресторана, и у всех гостей нет интернета», в
котором гость просто зовёт официанта. Не делать.

### Частичный (медленная/рваная связь)

Отдельного режима **нет by design**: в кассовом пути edge никогда не ждёт
облако синхронно. Все взаимодействия с облаком — фоновый sync-агент (§3) с
таймаутами и ретраями; медленная связь означает лишь «лаг синхронизации
больше». Единственные синхронные вызовы в облако — некритичные (handoff
preview): им таймаут 3–5с и явная ошибка в UI.

Правило для всего будущего кода edge: **облачный вызов на кассовом пути —
запрещён.** Это архитектурный инвариант, а не настройка.

## 3. Синхронизация

Два независимых потока с разной природой — и это главное проектное решение:

```
edge ──(факты: append-only события)──► cloud     продажи, смены
edge ◄──(состояние: версионированные снапшоты)── cloud     каталог, цены, сотрудники, столы
```

### 3.1 edge → cloud: append-only журнал фактов

Каждая команда POS в той же локальной транзакции пишет событие в таблицу
`sync_outbox` (id UUID, seq BIGSERIAL, type, payload jsonb, occurred_at).
Событийные типы — те же, что уже перечислены в `docs/EVENTS.md` для
outbox-механики (ShiftOpened, TicketLinesAdded, TicketFired, ShiftClosed, …) —
edge просто даёт мёртвому сейчас outbox'у (§4 DDD-отчёта) первого реального
потребителя.

Sync-агент: цикл «взять батч seq > last_acked → `POST /api/v1/sync/events`
(HTTP, с ретраем и экспоненциальной паузой) → облако отвечает last_acked».
Облако применяет события идемпотентно (event UUID = ключ дедупликации,
`INSERT ... ON CONFLICT DO NOTHING`) в свои pos-таблицы-проекции.

**Почему это проще CRDT.** CRDT решает задачу «N реплик конкурентно меняют
одно значение, и все правы». У продаж этой задачи нет:

- Событие продажи — **факт из физического мира**: официант нажал, чек
  напечатан. Факты не конфликтуют, их не с чем мержить — их только доставляют.
- Writer один: pos-состояние ресторана пишет только его edge. Облако держит
  read-проекцию и **никогда не пишет в pos-сущности edge-ресторана**. Нет
  двунаправленной записи → нечего разрешать.
- Нужен только порядок внутри одного edge — его даёт локальный `seq`
  (BIGSERIAL). Глобальный порядок между ресторанами не нужен: тенанты
  независимы.
- CRDT-цена (специальные типы данных, тумбстоуны, merge-функции на каждое
  поле, невозможность инвариантов вида «одна открытая смена») не покупает
  ничего, что нужно кассе.

### 3.2 cloud → edge: версионированные снапшоты

Каталог/цены/столы/сотрудники — это **текущее состояние**, история изменений
edge'у не нужна. Семантика compacted topic («последняя версия каждой
сущности») достигается без брокера: облако держит на каждую сущность-коллекцию
монотонную ревизию (bump при любой правке — по сути тот же механизм, что уже
кормит ETag в `pos/state`), edge периодически (и по push-подсказке, когда связь
есть) спрашивает `GET /api/v1/sync/catalog?rev=N` и получает либо 304, либо
полный снапшот `rev=M`, который применяет атомарно (транзакция: очистить
проекцию → залить → записать rev). Полный снапшот вместо диффов: каталог
ресторана — сотни строк, это килобайты; дифф-протокол — сложность без выгоды.

Тикеты не страдают от подмены каталога под ногами — строки снапшотятся при
добавлении (уже так).

### 3.3 Протокол: сравнение вариантов

| Вариант | Оценка |
|---|---|
| **Kafka на edge** | ❌ Слишком тяжело — не столько по железу (KRaft-single-node запустится), сколько по ops: брокер в каждом ресторане без админа, апгрейды, диски, мониторинг; плюс ключевое — durable-запись события обязана быть **в одной транзакции с продажей**, а Kafka-продюс в транзакцию Postgres не входит → outbox-таблица нужна всё равно, и брокер оказывается лишним хопом |
| **NATS leaf nodes** | ⚠️ Технически создан ровно для этой топологии (leaf в ресторане, hub в облаке, store-and-forward через JetStream), один лёгкий бинарь. Но: тот же outbox-аргумент (транзакционность с БД не даётся бесплатно), новый компонент со своей моделью безопасности/учёток на каждый тенант, и он решает только транспорт — который у нас уже есть: HTTP до облака. Кандидат на будущее, когда появится fan-out (KDS-экраны, несколько подписчиков на события edge) |
| **Очередь в локальной БД + HTTP push/pull** | ✅ Outbox в той же транзакции (гарантия «продажа записана ⇒ будет доставлена»), транспорт — уже существующий HTTP-стек `net/http` + auth, дедуп — `ON CONFLICT`, ретраи — цикл с паузой. Ноль новых компонентов |

**Решение: outbox в локальном Postgres + HTTP.** Где потребуется топик в
облаке (веер на потребителей — аналитика, AI), sync-endpoint облака публикует
принятые события в облачную шину — это облачная забота, edge о ней не знает.

## 4. Конфликты

### Почему их почти нет

Сформулировано в §3.1: append-only факты + single writer на каждый класс
данных. Матрица владения:

| Данные | Writer | Все остальные |
|---|---|---|
| Смены, тикеты, строки ресторана | его edge | read-only проекция |
| Каталог, цены, столы, сотрудники, темы | облако | read-only проекция на edge |
| Handoff, гостевые заказы, CRM | облако | edge читает при связи |

Пересечения записи нет ни по одной таблице → merge-конфликтов нет по
построению.

### Где конфликты всё же есть и что делать

1. **Правка каталога в облаке, пока edge офлайн.** Официант продаёт по цене
   rev N, менеджер уже поднял цену в rev M. Это не конфликт данных — строки
   снапшоты, продажа по старой цене консистентна и юридически верна («цена на
   витрине в момент продажи»). Это **бизнес-лаг**, и лечится он видимостью:
   в админке у ресторана показывать `catalog rev на edge` / `последний sync`;
   стухший edge (> X часов) — алерт менеджеру, не блокировка кассы.

2. **Попытка править каталог с edge** (86 позиций, «блюдо закончилось»).
   В базовой модели — запрещено (каталог read-only). Но stop-list — реальная
   кассовая нужда, официант должен уметь снять блюдо офлайн. Решение, не
   ломающее single-writer: `available` на edge — это **оверлей** (локальная
   таблица `item_stoplist`), который (а) применяется поверх проекции при
   отдаче `pos/state`, (б) уезжает в облако обычным outbox-событием
   («ItemStoppedAtEdge»), облако решает, отражать ли в паблишинге. Сам каталог
   edge не трогает.

3. **Один тикет с двух устройств.** До этапа 3 невозможно (один терминал).
   На этапе 3 конфликт **не возникает by design**: терминалы — тонкие клиенты
   edge-сервера (модель iikoFront main/slave), вся запись идёт через один
   pos-app-процесс, конкурентность разруливают существующие БД-инварианты
   (partial unique «один open ticket на стол», «одна открытая смена») — два
   официанта, добавляющие в один стол, просто аппендят строки в один тикет,
   это легально. Peer-to-peer синк терминалов не делать никогда.

4. **Двойная доставка события** (ретрай после потерянного ack) — не конфликт,
   а дедуп: event UUID + `ON CONFLICT DO NOTHING` (§3.1).

5. **Handoff-код принят, связь упала до consume-ack.** Consume — облачная
   операция; accept на POS при офлайне недоступен (§2), значит частичных
   состояний саги на edge не бывает.

## 5. Идентификаторы и часы

### Идентификаторы

- Все ID уже UUID (stdlib `uuid`, Go 1.27) и генерируются на стороне пишущего —
  edge генерирует ID смен/тикетов/строк сам, коллизий с облаком нет,
  переприсвоения при синке нет (ключевое отличие от «int-sequence в облаке»,
  которое сделало бы офлайн невозможным). Рекомендация: для новых edge-сущностей
  использовать **UUIDv7** — время в старших битах даёт сортируемость и дешёвые
  индексы; семантический порядок это не заменяет (см. ниже про seq).
- Человекочитаемые номера («shift-N», будущий номер чека) — **локальная
  последовательность edge** (per restaurant, per till), присваивается в момент
  операции, в облако едет как атрибут факта. Облако номера не выдаёт и не
  перенумеровывает — иначе офлайн-чек остался бы без номера. Текущий
  `ShiftSequence` (вычисление ordinal по opened_at) на edge работает как есть.

### Часы: event time ≠ sync time

Каждое событие несёт два времени, и путать их нельзя:

- `occurred_at` — часы edge в момент операции (**business time**; печатается
  на чеке, определяет смену);
- `received_at` — часы облака в момент приёма (**sync time**; только
  диагностика лага, в отчётность не попадает никогда).

Порядок событий определяет `seq`, а не таймстемп — поэтому дрейф часов edge
не ломает корректность, только косметику. На edge — обычный NTP; при
недоступности NTP касса продолжает работать (инвариант §2), облако при приёме
помечает события с `occurred_at` из будущего/глубокого прошлого флагом
`clock_suspect` для разборов.

### Кассовая сверка при поздней синхронизации

- **Смена — единица сверки, и она закрывается на edge.** Z-отчёт
  (expected/declared/variance) вычисляется локально в момент `CloseShift` и
  приезжает в облако готовым фактом внутри события. Облако его **не
  пересчитывает** — иначе гонка «пересчитали по неполным данным». (Это ещё
  один довод в пользу пункта 1 из топ-10 DDD-отчёта — атомарный CloseShift
  одной транзакцией: на edge он становится источником истины для денег.)
- Отчёты облака привязываются к **business date смены** (`opened_at`), а не к
  дате прихода данных: смена, досинхронизировавшаяся во вторник, ложится в
  понедельник.
- Полнота: облако хранит `last_acked_seq` и `last_seen_at` per edge; любой
  отчёт, где участвуют edge-рестораны, показывает «данные полны на момент
  <минимальный last_seen>» — вместо молчаливо неполных цифр. Это же поле
  кормит алерт «edge не выходил на связь X часов».

## 6. Локальная разработка: compose-профиль `edge`

Расширение `deploy/docker-compose.yml` через
[profiles](https://docs.docker.com/compose/profiles/) — cloud-стек не меняется,
edge поднимается только по `--profile edge`:

```yaml
  # docker compose -f deploy/docker-compose.yml --profile edge up -d --build
  postgres-edge:
    profiles: [edge]
    image: postgres:16
    environment: { POSTGRES_DB: aivo_edge, POSTGRES_USER: aivo, POSTGRES_PASSWORD: aivo }
    volumes: [aivo_edge_pgdata:/var/lib/postgresql/data]

  aivo-edge:
    profiles: [edge]
    build: { context: .., dockerfile: deploy/Dockerfile }   # тот же образ
    depends_on: [postgres-edge]
    restart: on-failure
    environment:
      MODE: edge
      DATABASE_URL: postgres://aivo:aivo@postgres-edge:5432/aivo_edge?sslmode=disable
      CLOUD_URL: http://aivo-server:8080        # sync-агент ходит сюда
      EDGE_RESTAURANT_ID: <из aivo-seed>        # какой тенант обслуживаем
      EDGE_SYNC_TOKEN: dev-edge-token           # аутентификация edge в облаке
    ports: ["8081:8080"]                        # POS официанта: localhost:8081/pos
```

Имитация обрыва связи — самым тупым работающим способом, без toxiproxy:

```bash
# deploy/edge-link.sh
docker network disconnect aivo_default aivo-aivo-edge-1   # "интернет упал"
docker network connect    aivo_default aivo-aivo-edge-1   # "интернет вернулся"
```

`disconnect` рвёт edge↔cloud, но публикуемый порт 8081 (терминал↔edge,
«локальный Wi-Fi ресторана») продолжает работать — топология обрыва честная.
Toxiproxy добавить, только когда понадобится тестировать именно
медленную/рваную связь (latency/bandwidth-токсики), для обрыва он не нужен.

### Сценарий демо

1. `docker compose --profile edge up -d --build`; `aivo-seed` — демо-тенант;
   edge стартует, стягивает снапшот каталога (лог: `catalog synced rev=1`).
2. Открыть `localhost:8081/pos`, залогиниться официантом, открыть смену,
   пробить тикет на стол 3, fire.
3. В облачной админке (`localhost:8080/admin`) видно: смена открыта, продажи
   идут (доехали через sync).
4. `edge-link.sh disconnect` — «интернет упал». POS показывает офлайн-баннер,
   но: пробить ещё два тикета, поменять цену блюда в облачной админке
   (до edge не доходит — в тикете старая цена-снапшот), попытаться принять
   handoff — честная ошибка «нет связи».
5. `edge-link.sh connect`. Через секунды: продажи офлайн-периода появляются в
   облаке, новая цена приезжает на edge (следующая продажа — по новой).
6. Закрыть смену на edge — Z-отчёт с variance виден в облаке как есть.

Это демо — одновременно приёмочный тест этапа 2.

## 7. Поэтапный путь от текущего монолита

### Этап 0 — сейчас: всё в облаке

Ничего не строить, но два гигиенических действия, которые обязаны случиться
до любого этапа:

- **Убрать тихий мок-фолбэк** в `frontend/pos/src/api.ts` (Proxy →
  mockActive при status 0): заменить на явный офлайн-баннер и ретрай поллинга.
  Сейчас обрыв сети = официант незаметно работает «в песочнице».
- Зафиксировать инвариант «облачный вызов на кассовом пути запрещён» и
  атомарный `CloseShift` (топ-1 DDD-отчёта) — edge унаследует этот код как
  money path.

### Этап 1 — PWA-кеш и очередь в POS-фронте (дёшево, недели)

Переживает **короткие** обрывы (минуты) без серверной работы:

- Service worker: кэш SPA-оболочки + последнего снапшота `pos/state`
  (каталог, столы, открытые тикеты) — экран не слепнет при обрыве.
- Очередь исходящих команд в IndexedDB: `addLines`/`fire` при офлайне
  становятся pending-операциями с client-generated UUID строк, UI показывает
  их как «не отправлено», при восстановлении связи — replay по порядку.
  Серверу нужна одна мелочь: идемпотентность add-lines по client line UUID
  (дедуп повторной отправки).
- Открытие/закрытие смены офлайн — **не поддерживать** на этом этапе (редкая
  операция, требует серверных инвариантов; честная ошибка «нет связи»).

Потолок этапа: состояние живёт в браузере одного телефона (чистка storage =
потеря очереди), печати нет, второй терминал не видит офлайн-тикеты первого.
Это осознанный мост, не замена edge.

### Этап 2 — edge-бинарь (ядро всей темы)

Всё из §1–§6: `MODE=edge`, локальный Postgres, каталог-проекция + auth-кэш,
`sync_outbox` + HTTP push/pull, compose-профиль, демо-сценарий. PWA-очередь
этапа 1 остаётся в коде, но практически не срабатывает — API теперь в
локальной сети. Порядок работ внутри этапа:

1. sync-endpoint'ы в облаке (`POST /sync/events` идемпотентный,
   `GET /sync/catalog?rev=`) + auth edge-узла (токен per restaurant);
2. режимный запуск бинаря (маршруты и фоновые агенты по `MODE`);
3. sync-агент на edge (два цикла: push outbox, pull snapshot);
4. проекции в облаке + отчётность по business date + индикатор «данные полны
   на …» и алерт стухшего edge.

### Этап 3 — мульти-терминал

- Терминалы (телефоны, планшеты, стационарная касса) — тонкие клиенты
  edge-сервера по локальной сети; **никакого состояния на терминале** кроме
  PWA-кэша этапа 1. Подключение — QR с адресом edge + логин сотрудника.
- Конкурентность решает edge-Postgres существующими инвариантами; для живости
  экранов поднять поллинг `pos/state` до 1–2с или SSE — в локальной сети это
  бесплатно.
- `till` перестаёт быть «always 1»: несколько касс = несколько параллельных
  смен per till, `other_till_shift` начинает заполняться — модель в контракте
  это уже предусматривает (`docs/PLATFORM.md`, pos/state).
- Отказоустойчивость самого edge-узла (вторая коробка, failover) — **не
  делать**: вероятность «умер mini-PC» ≪ «упал интернет», ремонт — замена
  коробки + восстановление из облака (edge-состояние после полного синка
  восстановимо: снапшот каталога + проекции открытой смены). Держать это
  свойство — «edge восстановим из облака» — как ограничение дизайна.

## Итого: решения одним экраном

| Вопрос | Решение |
|---|---|
| Edge-узел | тот же `aivo-server`, `MODE=edge`; только pos + проекции |
| СУБД на edge | локальный Postgres (переиспользование sqlc/миграций); SQLite — только если железо заставит |
| Гостевое меню при офлайне ресторана | из облака по LTE гостя; с edge не раздаём |
| Handoff при офлайне | недоступен, честная ошибка |
| edge→cloud | append-only события через `sync_outbox` (транзакция с продажей) + HTTP push, дедуп по event UUID |
| cloud→edge | версионированные полные снапшоты каталога/сотрудников, atomic swap |
| Брокер на edge | нет (ни Kafka, ни NATS); NATS leaf — кандидат при появлении fan-out |
| Конфликты | устранены single-writer-матрицей + снапшот-строками; stop-list — оверлей |
| ID | UUID, генерируются на edge (v7 для новых); чековые номера — локальные последовательности |
| Время | occurred_at (business) ≠ received_at (sync); порядок — seq; отчёты — по business date смены + индикатор полноты |
| Сверка | Z-отчёт считается на edge при закрытии, облако не пересчитывает |
| Dev | compose-профиль `edge`, обрыв = `docker network disconnect` |
| Путь | 0: убрать мок-фолбэк → 1: PWA-очередь → 2: edge-бинарь → 3: тонкие мульти-терминалы |
