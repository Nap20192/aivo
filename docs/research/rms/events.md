# Событийная архитектура AIVO: outbox → Kafka

Проектный отчёт. Код не меняется; это контракт для реализации. Исходные данные:
`docs/EVENTS.md` (каталог событий), `backend/migrations/platform/0004_events.up.sql`
(outbox), `internal/sharedkernel` (`DomainEvent`, `AggregateRoot.Raise`),
`docs/research/ddd-architecture.md` §4 (правило «порт vs событие», outbox мёртв),
`docs/PLATFORM.md`. Сейчас вся система — один Go-процесс + Postgres; цель —
путь к отказоустойчивой шине при росте в полноценную RMS (референс iiko), без
преждевременной инфраструктуры.

**Главный принцип: Postgres outbox — источник истины, Kafka — транспорт.**
Событие «существует», когда его строка закоммичена в `events` в одной транзакции
с изменением агрегата. Kafka можно потерять, пересоздать, переналить из outbox —
ничего не пропадёт. Это же делает всю миграцию поэтапной: контракт для
продюсеров и консьюмеров один и тот же на всех этапах, меняется только транспорт.

## 0. Путь: три этапа

Порядок подключения — из ddd-architecture.md §4: паблишер появляется только
с первым реальным потребителем, никакого event bus поверх пустого outbox.

### Этап 0 — outbox живёт, консьюмеры читают таблицу (без Kafka вообще)

- App-слой после команды: `aggregate.Events()` → INSERT в `events` **в той же
  транзакции**, что и изменение агрегата. Первые проводные события — те, у
  которых уже есть потребитель: `AssistantActionsApplied` (аудит AI вместо slog)
  и `OrderPlaced`/`TicketClosed` (CRM-проекция вместо прямого SQL по чужим таблицам).
- Один in-process **диспетчер**: горутина поллит `events_pending` (индекс уже
  есть), отдаёт батч зарегистрированным Go-хендлерам последовательно, по успеху
  всех — `SET published_at = now()`. Ошибка хендлера — батч не помечается,
  ретрай на следующем тике (at-least-once, хендлеры идемпотентны по `id`).
- sqlc-запросы `events_pending`/`mark published` уже написаны
  (`queries/platform/platform.sql:11-14`) — диспетчер собирается из готовых кусков.
- Kafka на этом этапе **не нужна и не поднимается**. Этап 0 — это несколько
  дней работы и он самодостаточен, пока все консьюмеры живут в том же процессе.

### Этап 1 — relay в Kafka

- Появляется первый консьюмер, которому плохо в основном процессе (тяжёлая
  аналитика, отдельный сервис, KDS). Поднимается брокер (§7) и **relay** —
  та же поллящая горутина, но вместо вызова Go-хендлеров публикует в Kafka
  и лишь потом ставит `published_at`.
- In-process хендлеры этапа 0 переезжают на Kafka-консьюмер-группы **или**
  остаются как были — семантика `published_at` меняется с «доставлено
  хендлерам» на «доставлено в транспорт», контракт событий не меняется.
- Publish обязательно с `acks=all` и включённой идемпотентностью продюсера;
  крэш между publish и UPDATE даёт дубль в топике — это нормальный
  at-least-once, консьюмеры и так дедуплицируют по `id`.

### Этап 2 — внешние консьюмеры

- Отдельные процессы/сервисы (KDS, аналитика, интеграции) подписываются на
  топики со своими consumer group. Основной процесс их существования не
  замечает. Появление второго процесса — тот момент, когда ADR 0001
  («no gRPC until a second process needs it») пересматривается для
  синхронных вызовов, но событийная часть уже готова.

Триггеры перехода: этап 0 → 1 — первый потребитель вне основного процесса
или поток событий, мешающий основному циклу; этап 1 → 2 — сам факт появления
внешнего сервиса. Не по календарю, а по потребности.

### Одна миграция перед этапом 0: колонка `seq`

```sql
ALTER TABLE events ADD COLUMN seq bigint GENERATED ALWAYS AS IDENTITY;
CREATE UNIQUE INDEX events_seq ON events (seq);
```

Зачем: `occurred_at` — это `now()` транзакции (время её начала), при
конкурентных транзакциях порядок таймстампов не совпадает с порядком коммитов.
Для одного агрегата это не страшно (row lock сериализует транзакции), но
relay'ю нужен стабильный тотальный порядок выборки и курсор. Поллинг меняется
на `ORDER BY seq`. Оговорка: у `seq` есть «дыры видимости» (транзакция с
меньшим seq может закоммититься позже уже прочитанного большего) — поэтому
relay **не** ведёт водяной знак по seq, а помечает каждую строку
`published_at` индивидуально; `events_pending` никого не теряет. Отставшая
строка уйдёт в топик чуть позже соседей — межагрегатный порядок мы и не
обещаем (§2).

Ретеншн outbox: опубликованные строки старше 30 дней удалять фоновым джобом
(`DELETE ... WHERE published_at < now() - interval '30 days'` батчами).
Outbox — журнал доставки, не event store (§6).

## 1. Relay: Debezium CDC vs самописный поллер

| | Debezium (CDC outbox routing) | Самописный поллер |
|---|---|---|
| Механика | логическая репликация Postgres (wal_level=logical, слот) → Kafka Connect → SMT outbox router | горутина: `SELECT ... WHERE published_at IS NULL ORDER BY seq LIMIT N` → produce → `UPDATE published_at` |
| Инфраструктура | + Kafka Connect (JVM-кластер), конфиг коннектора, мониторинг слота репликации | ничего: код в существующем бинаре |
| Латентность | ~десятки мс | тик поллинга (0.5–1 с) — для CRM/аудита/аналитики безразлично |
| Нагрузка на БД | ноль поллинга, но неотслеживаемый слот репликации при падении Connect **распухает WAL до отказа диска** | один дешёвый индексный SELECT в секунду по частичному индексу `events_pending` |
| Failure modes | свои: рестарты коннекторов, версии плагинов, права репликации, managed-Postgres-ограничения | наши же: Go-код, slog, обычные ретраи |
| Масштабный потолок | десятки тысяч событий/с | тысячи событий/с на одном поллере — на порядки выше нашей нужды |

**Выбор: самописный поллер.** Ресторанная нагрузка — это сотни событий в
минуту на весь SaaS в обозримой перспективе; поллер — ~150 строк Go в том же
бинаре, без единой новой движущейся части. Debezium добавляет JVM-кластер и
класс отказов «слот репликации съел диск» ради латентности, которая никому
здесь не нужна. Точка пересмотра: устойчиво > ~500 событий/с или требование
латентности < 100 мс — тогда Debezium ставится **рядом**, не меняя контракт
(outbox-таблица — ровно тот формат, который ест его outbox event router).

Деталь реализации поллера:

- Один инстанс (мы и так один процесс). Advisory lock
  (`pg_try_advisory_lock`) на старте — защита от случайного второго бинаря.
  Несколько relay-инстансов с `FOR UPDATE SKIP LOCKED` — только когда
  появится второй процесс приложения, не раньше.
- Батч 100–500 строк, publish синхронно с `acks=all`, UPDATE помеченных —
  одним запросом по списку id, в порядке seq.
- Клиент — `franz-go` (twmb/franz-go): чистый Go, без CGo/librdkafka,
  один клиент на продюсер и консьюмеры.

## 2. Топология Kafka

### Топики — по bounded context

```
aivo.platform.events   (org- и restaurant-уровень платформы)
aivo.menu.events       (заказы, сервис-запросы, handoff)
aivo.pos.events        (смены, тикеты)
```

- **Не по агрегату**: 12+ топиков при пяти событиях на брата — администрация
  ради администрации; консьюмерам первой волны (CRM, аналитика) всё равно
  нужны события нескольких агрегатов сразу.
- **Не один общий**: контексты растут с разной скоростью, ретеншн и права
  доступа проще держать по контексту; название топика = граница владения
  (контекст-владелец пишет, остальные читают — совпадает с картой контекстов).
- Роутинг в relay тривиален: префикс имени события → контекст (таблица
  соответствия из `docs/EVENTS.md`, захардкоженная map в коде relay).

### Ключ партиционирования — `restaurant_id`

Kafka гарантирует порядок только внутри партиции. Единица, внутри которой
порядок бизнес-значим, — ресторан: жизнь смены (`ShiftOpened` → `TicketOpened`
→ `LinesFired` → `TicketClosed` → `ShiftClosed`), поток заказов зала, handoff.
Кросс-ресторанного порядка не существует как бизнес-понятия — рестораны
независимые тенанты. Поэтому:

- `key = restaurant_id` → все события одного ресторана в одной партиции →
  каждый консьюмер видит их строго в порядке публикации. KDS и CRM получают
  корректную последовательность «открыли тикет → закрыли тикет» бесплатно.
- Org-уровневые события (`OrganizationRegistered`, `SubscriptionChanged`,
  `restaurant_id IS NULL`) — `key = org_id` (он есть в payload). Порядок
  смен подписки на орг тоже сохраняется.
- Побочный бонус: горячий тенант размазывается не более чем на одну
  партицию и не ломает порядок остальных.
- Число партиций: **12 на топик** сразу. Партиции почти бесплатны, а
  добавление их потом ломает маппинг key→partition (§4). 12 хватит на
  годы роста консьюмер-параллелизма.

### Retention и compaction

- Все три топика: `retention.ms = 30 дней`, `cleanup.policy = delete`.
  Kafka — транспорт; полная история навсегда живёт в outbox/БД. Новому
  консьюмеру, которому нужна история глубже ретеншена, делается backfill
  из outbox (перечитать `events` по `seq` тем же relay-кодом в отдельный
  топик или напрямую в проекцию) — это дешевле, чем хранить в Kafka вечно.
- **Compacted-топики — не заводить.** Компакция нужна для «последнего
  состояния по ключу» (справочники: рестораны, меню, темы). У нас
  консьюмеры по конвенции `docs/EVENTS.md` дочитывают нужное состояние из
  БД/API («payload плоский, консьюмеры перечитывают состояние сами»).
  Compacted `aivo.platform.restaurants` появится тогда, когда внешний
  сервис не сможет ходить в наш API за справочником — не раньше.

## 3. Схемы сообщений

### Конверт — свой, плоский, зеркало outbox-строки

```json
{
  "id": "0198c9c2-...-uuid",
  "name": "OrderPlaced",
  "version": 1,
  "aggregate_type": "order",
  "aggregate_id": "0198c9c2-...",
  "restaurant_id": "0198c9c2-...",
  "occurred_at": "2026-08-24T12:34:56.789Z",
  "payload": { "order_id": "...", "table_id": "...", "total_cents": 4200 }
}
```

Kafka message: `key = restaurant_id` (или org_id), `value` = конверт целиком,
заголовки `event-name` и `event-version` дублируются в Kafka headers — чтобы
консьюмер мог фильтровать/роутить, не парся JSON.

**Почему не CloudEvents.** Конверт выше — это CloudEvents с точностью до
переименований (`name`→`type`, `occurred_at`→`time`, + обязательные
`source`/`specversion`). CloudEvents окупается при интеграции с чужими
системами (брокеры-триггеры, коммерческие подписчики). У нас все консьюмеры
свои; платить ceremony-полями и маппингом сейчас не за что. Если внешняя
интеграция потребует CE — это механическая обёртка на границе relay, один
маппер, контракт внутри не меняется. Решение зафиксировать так: **имена полей
конверта — стабильный контракт**, менять их нельзя, добавлять можно.

### Эволюция схем без Schema Registry

Registry — это сервис + клиентские библиотеки + процесс согласования ради
защиты от несогласованных команд. Пока продюсер и все консьюмеры живут в
одном репозитории, ту же защиту даёт компилятор и код-ревью:

1. **Контракт в репозитории.** `docs/EVENTS.md` остаётся человеческим
   каталогом; рядом — Go-типы payload'ов по одному пакету на контекст
   (например `internal/menu/events`). Продюсер и in-process консьюмеры
   используют одни типы — рассинхрон ловится компилятором. Для внешних
   консьюмеров на этапе 2 из этих типов при желании генерятся JSON Schema —
   не раньше, чем внешний консьюмер появится.
2. **Правила совместимости (аналог BACKWARD):**
   - можно: добавить необязательное поле payload; добавить новое событие;
   - нельзя: удалить/переименовать поле, изменить тип или семантику,
     сделать необязательное обязательным;
   - консьюмеры — tolerant reader: игнорируют незнакомые поля, не падают
     на отсутствии необязательных.
3. **Версионирование.** Поле `version` в конверте, стартует с 1. Breaking
   change → `version: 2`; переходный период продюсер может писать оба
   события (v1 и v2) либо консьюмеры обновляются до продюсера — при одном
   репозитории обычно достаточно второго. Имя события не трогаем
   (`OrderPlaced` навсегда `OrderPlaced`); суффиксы `.v2` в имени — только
   если однажды придётся разводить версии по разным топикам, что при нашем
   ретеншене в 30 дней маловероятно.
4. Registry ставится, когда продюсер и консьюмер окажутся в разных репо у
   разных команд — вместе с этапом 2 или позже.

Уже сейчас (дёшево, до этапа 0) — правки каталога из ddd-architecture.md §4:
убрать `code` из `HandoffCreated` (секрет в outbox), добавить
`ServiceRequestClosed`, `TicketLinesAdded`, `AssistantActionsApplied/Discarded`.

## 4. Надёжность

Целевая семантика тракта — **at-least-once end-to-end**:
транзакционный outbox не теряет события; relay может задублировать
(крэш между produce и UPDATE); идемпотентный продюсер franz-go убирает
дубли ретраев продюсера, но не дубли relay; консьюмеры обязаны
дедуплицировать. Всё exactly-once строится на стороне консьюмера, а не шины.

### Идемпотентность консьюмеров — по `event.id`

Два допустимых приёма, по ситуации:

- **Естественная идемпотентность** — когда обработка и так upsert:
  CRM-проекция `INSERT ... ON CONFLICT (customer_id, restaurant_id) DO UPDATE`
  от повторного `TicketClosed` c тем же id не изменится, только если апдейт
  выражен через факт («учесть тикет X»), а не дельту («+4200 к спенду»).
  Дельтовые апдейты естественной идемпотентности **не имеют** — им нужен:
- **Журнал обработанного**: таблица у консьюмера
  `processed_events(consumer text, event_id uuid, PRIMARY KEY (consumer, event_id))`;
  вставка в неё — в одной транзакции с эффектом обработки. Дубль → конфликт
  PK → скип. Чистка — вместе с ретеншеном (обработанное старше ретеншена
  топика можно удалять: старее ничего не приедет).

Правило по умолчанию: аудит и аналитика — журнал; проекции — переписывать
апдейты в форму факта, где не выходит — журнал.

### Ретраи и DLQ

- Оффсеты коммитятся **после** успешной обработки (никакого auto-commit
  «прочитал = обработал»).
- Транзиентная ошибка (БД недоступна, таймаут): ретрай на месте с
  экспоненциальным бэкоффом, партиция стоит. Это осознанно: перескок через
  событие ломает порядок ресторана, а пауза одной партиции задевает только
  рестораны этой партиции.
- Постоянная ошибка (кривой payload, бизнес-инвариант): после N=5 попыток —
  в DLQ-топик `<topic>.dlq.<group>` (например
  `aivo.pos.events.dlq.crm-projector`) с заголовками `error`,
  `original-partition`, `original-offset`, оффсет коммитится, партиция едет
  дальше. DLQ по группе, не общий: у каждого консьюмера своя причина падать.
- DLQ обрабатывается руками: алерт на ненулевой lag DLQ-топика, разбор,
  фикс кода, переигрывание утилитой (прочитать DLQ → снова в основной
  обработчик). Автоматический re-drive не строить (§6).

### Порядок при репартиционировании

Увеличение числа партиций меняет `hash(key) % partitions` → события одного
ресторана начинают попадать в новую партицию, и консьюмер может увидеть
новые события раньше неразгребённого хвоста в старой. Политика:

1. Не наступать на проблему: 12 партиций с запасом (§2), партиции не
   добавлять годами.
2. Если всё же надо: пауза relay → дождаться нулевого lag всех групп →
   увеличить партиции (или создать `-v2` топик и переключить relay) →
   возобновить. Outbox в это время копит события, ничего не теряется —
   ещё один дивиденд «истина в Postgres».
3. Консьюмерам, которым порядок критичен (KDS), в любом случае держать
   guard от прошлого: игнорировать событие, если проекция уже видела более
   позднее состояние агрегата (сравнение по `occurred_at`/статусу из БД).

## 5. Консьюмеры первой волны

| Консьюмер | Группа | Топики | События | Идемпотентность |
|---|---|---|---|---|
| CRM-проекция (guest visits/spend, `docs/PLATFORM.md` CRM API) | `crm-projector` | `aivo.menu.events`, `aivo.pos.events` | `OrderPlaced`, `TicketClosed` (с `customer_id`) | журнал `processed_events` — спенд дельтовый |
| Аудит AI-действий (вместо slog) | `ai-audit` | `aivo.platform.events` | `AssistantActionsApplied`, `AssistantActionsDiscarded`, `ThemeApplied(source=ai_proposal)` | append-only журнал с PK по event id |
| Аналитика/отчёты (выручка, смены, вариансы) | `analytics` | все три | практически все; минимум: `TicketClosed`, `ShiftClosed`, `OrderPlaced`, `SubscriptionChanged` | журнал; агрегаты пересчитываемы из outbox |
| KDS (будущий) | `kds` | `aivo.pos.events`, `aivo.menu.events` | `LinesFired`, `TicketClosed`, `OrderPlaced`, `TicketOpened` | естественная (проекция состояния тикета) + guard порядка (§4) |

Все четверо стартуют на этапе 0 как in-process хендлеры того же диспетчера
(кроме KDS — его ещё нет); на этап 1–2 переезжают без смены логики — меняется
только источник (таблица → топик). Ни один не пишет в чужие таблицы напрямую —
каждый владеет своими проекциями; это и есть выигрыш против сегодняшнего
«CRM прямым SQL по чужим таблицам».

## 6. Анти-скоуп: что НЕ делаем и почему

- **Event sourcing.** Агрегаты живут в нормальных таблицах, outbox — журнал
  доставки, не store of record. ES тянет снапшоты, версионирование потоков,
  миграции событий — цена огромна, а выгода (полная история) у нас уже есть
  в outbox на 30 дней и в обычных таблицах навсегда.
- **Exactly-once / Kafka-транзакции.** `read_committed` + transactional
  producer защищают только цепочки Kafka→Kafka. Наши консьюмеры пишут в
  Postgres — там exactly-once даёт дедуп по event id (§4), бесплатно и
  понятно. Транзакционный продюсер в relay не нужен: дубль перекрывается
  той же дедупликацией.
- **Kafka Streams / Flink.** Стриминговых join'ов и оконных агрегаций нет;
  все проекции — «событие → UPDATE в Postgres». Go-консьюмер на franz-go
  покрывает всё. Пересмотр — при реалтайм-аналитике с окнами (и то сначала
  посмотреть на materialized views).
- **Schema Registry** — §3: один репозиторий, компилятор дешевле сервиса.
- **Debezium/CDC** — §1: поллер, пока < ~500 событий/с.
- **Compacted-справочники** — §2: консьюмеры читают состояние из БД/API.
- **Кластер из 3+ брокеров, MirrorMaker, multi-DC.** Один брокер (managed —
  предпочтительно) достаточен: даже при его смерти события копятся в outbox
  и доезжают после восстановления. Отказоустойчивость уровня «не потерять» у
  нас от Postgres; кластер — про «не остановиться», это понадобится вместе
  с внешними консьюмерами, у которых SLA.
- **Автоматический re-drive DLQ, saga-оркестратор, retry-топики с
  задержками.** Разбор DLQ руками при нашем потоке — минуты в месяц;
  единственная сага (AcceptHandoff) — синхронная, в `pos/app`, шине не
  принадлежит.
- **Уведомление поллера через LISTEN/NOTIFY.** Тик в 0.5–1 с даёт ту же
  практическую латентность без второго канала доставки и его failure modes.

## 7. Локальный дев: docker-compose

Сравнение одноброкерных вариантов:

| | `apache/kafka` (KRaft, без ZooKeeper) | `redpandadata/redpanda` |
|---|---|---|
| Процессы | 1 контейнер, JVM | 1 контейнер, нативный бинарь (C++) |
| RAM реально | ~1 ГБ (JVM heap + overhead) | ~200–500 МБ (`--memory 512M` честно работает) |
| Старт | ~10–20 с | ~2–3 с |
| Kafka API | эталон | совместим (без Streams/Connect-рантайма — они нам не нужны, §6) |
| UI | нет (сторонний kafka-ui) | `rpk` в комплекте + Redpanda Console |
| Паритет с продом | точный, если прод — managed Kafka (MSK/Confluent) | точный, если прод — Redpanda/Redpanda Cloud |

**Рекомендация: в compose — `apache/kafka` KRaft, один контейнер.**
Прод-мишень для «Kafka ради отказоустойчивости» — почти наверняка managed
Kafka; дев должен гонять тот же движок, чтобы ловить его особенности
(таймауты ребаланса, поведение acks) до прода. Redpanda — легитимный
своп одной строки compose, если гигабайт на JVM жмёт ноутбук; протокольный
контракт кода не меняется (franz-go работает с обоими). Решение «Redpanda и
в проде» — отдельный разговор про вендора, не про этот документ.

Эскиз сервиса в `deploy/docker-compose.yml` (добавляется на этапе 1, не раньше):

```yaml
  kafka:
    image: apache/kafka:4.0.0
    ports: ["9092:9092"]
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false"
    volumes: ["kafka-data:/var/lib/kafka/data"]
```

`AUTO_CREATE_TOPICS=false` принципиально: три топика создаются явно
(инит-скриптом или миграцией relay при старте) с 12 партициями и ретеншеном
из §2 — авто-создание дало бы дефолтную 1 партицию и молчаливо съело бы
партиционирование по ресторану. Приложение конфигурируется через
`KAFKA_BROKERS` (пусто = этап 0, диспетчер по таблице; задано = relay в Kafka) —
один и тот же бинарь на всех этапах.

## Сводка решений

| Вопрос | Решение | Пересмотр когда |
|---|---|---|
| Источник истины | Postgres outbox `events` (+ колонка `seq`) | никогда |

| Конверт | свой плоский JSON = outbox-строка + `version`; headers `event-name`/`event-version` | внешняя интеграция → CE-обёртка на границе |
| Схемы | Go-типы в репо + tolerant reader + additive-only; Registry — нет | консьюмеры в чужих репо |

| DLQ | `<topic>.dlq.<group>` после 5 ретраев, разбор руками | — |
| Дев-брокер | `apache/kafka` KRaft, 1 контейнер; Redpanda — своп при нехватке RAM | — |
