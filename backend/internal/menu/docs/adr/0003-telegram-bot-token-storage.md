# Telegram bot tokens: AES-256-GCM at rest via Go stdlib, not a KMS/Vault

Each Restaurant's Telegram bot token (per [ADR 0001](0001-per-restaurant-telegram-bot.md)) is a per-tenant third-party credential, stored encrypted at rest using AES-256-GCM (`crypto/aes`/`crypto/cipher`, Go stdlib, no new dependency), with the restaurant id as AEAD additional-data binding the ciphertext to its tenant. The master key comes from an env var or mounted secret file — the same code path whether self-hosted or cloud-deployed. A `key_version` column sits next to the ciphertext from day one, so a future master-key rotation or a move to a cloud KMS / HashiCorp Vault is a background re-wrap rather than a schema migration. Decryption is scoped to the single call site that talks to the Telegram API — the plaintext token is never logged, cached, or held as a Go `string` (only `[]byte`, zeroed after use).

Full envelope encryption via a cloud KMS or self-run Vault Transit is the "correct" long-term answer (HSM custody, built-in key versioning, rewrap-without-plaintext-exposure), but is infra this project can't assume for a self-hostable, early-stage OSS deployment — disproportionate today, and the `key_version` column exists specifically so upgrading to it later doesn't require revisiting every stored row's format. Named trade-off: no HSM custody, and the master key is a single point of failure if it leaks alongside DB access — acceptable for now, not permanent. Full research trail: `research/telegram-bot-token-storage` branch.
